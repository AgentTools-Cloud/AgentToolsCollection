About

The open discovery layer for the agent economy — x402 paid services, MCP servers, and A2A agents in one searchable, safety-scanned index.

Directory

A public, agent-readable index of three kinds of callable resources — x402 paid APIs, MCP servers, and A2A agents. Crawled from Smithery, the official MCP registry, Apify, Agenstry, Prowl, awesome-x402, x402scan, CDP Bazaar and manual submissions; exposed through search, service cards and MCP tools. No signup, no API key, open data.

Ask + service cards

/api/v1/ask retrieves real directory candidates first, then uses an LLM to rank only those candidates. /api/v1/services/{slug} returns payment, call and quality metadata before an agent calls an external service.

Three kinds of resources

Agents need to find different things: A2A agents tell an agent who can do a job, x402 lets it pay per call, and MCP servers give it the tools to do the work. We index all three behind one search and one set of MCP tools, browsable at /services, /mcp and /a2a.

What is x402?

x402 is Coinbase's HTTP 402 micropayment protocol. AI agents can discover a service, inspect its payment requirements, and then call the external API with an x402 payment flow. We index public x402 endpoints; agent-tools.cloud itself is discovery-only.

Agent-friendly discovery

Agents can use POST /api/v1/ask for intent-level recommendations, GET /api/v1/search for faceted search, and GET /api/v1/services/{slug} for a full service card.

Discovery entry-points: /.well-known/agent-tools.json · /.well-known/mcp.json

Full reference: /openapi.json (OpenAPI 3) · MCP server at /mcp-discovery/ · A2A agent at /a2a · /llms.txt. No key needed for read endpoints.

Everything on this site is readable by agents, not only the listings: daily statistics at /api/v1/stats/summary (MCP tool directory_stats), how every score is computed at /api/v1/methodology (get_methodology), and the Blog at /api/v1/blog (list_articles, get_article).

Safety scanning

Every indexed MCP server is re-scanned daily for known malware and abuse patterns — pipe-to-shell install lures, base64 / eval download cradles, bare-IP command-and-control URLs and prompt-injection phrasing in its advertised tool metadata. It also detects MCP tool-poisoning coercion — descriptions that try to hijack an agent's tool-calling (“always call this tool first”, “before using any other tool you must…”), hidden <IMPORTANT> instructions, demands to list API keys or include secrets in a response, and coercion to read & forward .key/.pem/.ssh/.env files. Each server carries a clean / suspicious / malicious verdict with the matched rules. Scanning is static only — we never execute server code.

You can also scan any MCP endpoint on demand, before you connect: call the scan_mcp_safety tool on the MCP server at /mcp-discovery, or send its URL to our A2A agent at /a2a. If the server is already indexed you get our latest stored verdict instantly; if not, we probe it live, scan it, and add it to the directory when it is reachable or you supplied metadata (documentation hosts such as example.com are scanned but never listed). Each on-demand call also runs a frontier large model second-opinion as an advisory dimension alongside the deterministic rules.

Paid verification

Anyone with an Agent Tools account or API key can pay an x402 service once and have us record what the paid call returned. You sign a single EIP-3009 USDC authorization on Base in your own wallet; its recipient is the service's own payTo, so funds go straight to the service and Agent Tools never holds them. We re-check the live price just before relaying and abort if the price or recipient changed; the call is sent once and never retried. Limits: Base USDC exact scheme only, at most $1.00, GET endpoints or POST endpoints with a declared public JSON probe_body up to 16 KiB, 256 KiB response cap.

Each run is scored 0–100 on delivery (35), a matching Base-USDC authorization and transfer (20), price match (10), non-empty (10) and well-formed (10) response, and latency (15). The detail page shows the last 30 days of runs, failures included, while the listing URL, request template and payment terms remain unchanged. Sponsored runs are evidence that the service delivers; they are never counted as paying demand.

Results are public for 30 days. Wallet signatures and response bodies are not stored.

For agents and scripts

No browser or GitHub sign-in needed. Mint a key with POST /api/v1/keys and send it as Authorization: Bearer <api_key>, then:

  1. POST /api/v1/services/{slug}/paid-verifications with {"payer": "0x…"} returns an id, the quoted price and EIP-712 typed_data.
  2. Sign typed_data with the payer wallet (eth_signTypedData_v4).
  3. POST /api/v1/paid-verifications/{id}/execute with {"signature": "0x…"} before valid_before; the response has status, http_status, tx_hash and score.

Over MCP (/mcp-discovery/): prepare_paid_verification(slug, payer) → sign typed_data → execute_paid_verification(id, signature) → get_paid_verification(id). Same API key, as header or api_key.

Recent results for any service are public in GET /api/v1/services/{slug} under paid_verification. Full schema: /openapi.json.

Grading

Every listing carries a 0–100 score and a letter grade, built only from signals we measure ourselves. We do not re-export another directory's rating.

x402 services

Availability20 Endpoint probe: ok 100%, degraded 45%, unknown 22%, down 0.
Payability15 Real HTTP 402 challenge 15, /.well-known/x402 descriptor 5, payment address 5, settlement network 3, price 2 — of 30, scaled to 15.
Demand35 Latest 30-day USDC receipts at the payTo address, read from the chain. Distinct payers carry two thirds (full at 1,000), transfer count one third (full at 10,000); both on a log scale. A wallet shared by several reachable listings is split between them, and more than 20 transfers per payer is discounted, down to half. Chains with no free indexer (currently Sui) leave this blank rather than zero.
Performance10 Latency of the last reachable probe: full marks at ≤ 200 ms, falling linearly to 0 at ≥ 2000 ms.

Owner verified5 Operator proved control of the domain.

A service whose endpoint is down is held at D regardless of the other components.

Re-scanning

Availability and on-chain demand are re-probed daily, and payment metadata on each verification pass. Grades recompute automatically after every pass — there is nothing to request. Each x402 listing page shows its own breakdown with the timestamps of the last two checks, and says why a component reads zero. The most common cause is that we could not extract a payment address from your 402 response or descriptor; publishing accepts[] with payTo, network and an amount fixes both that and the payability component.

Readiness score

Each detail page also shows a readiness score: nine criteria on how fully a listing follows its protocol and how it behaved in our probes over 30 days. The criteria follow the public Agenstry conformance methodology so operators see the same levers on both sites; how each one is measured is ours. Grades are fixed thresholds: A ≥ 90, B ≥ 75, C ≥ 60, D ≥ 40, F below.

Readiness vs. the quality grade

The quality grade above answers “is this usable right now, and how does it compare with its peers”: availability, speed and, for x402, on-chain demand, cut at percentiles of each kind. It sets search order and leaderboards. Readiness answers “how completely does this follow the standard”: signing, protocol version, declarations and a 30-day track record, on fixed thresholds. It is shown for reference and never changes search order. A fast endpoint with an unsigned, out-of-date card can rank high and read D; a complete, signed card on a slow host can read B and rank lower.

Adoption signals

Detail pages also show outside signs of use, when we can tie them to the listing: GitHub stars, forks and last push for the source repository, npm downloads over the last 30 days for a published package, and the Tranco rank of the listing's own website. Shared platforms (GitHub, gateways, hosting domains) are never credited to a single listing. Repositories refresh weekly, packages and ranks daily. These signals are display only: they change neither the quality grade nor the readiness score. They are in each detail API response as popularity.

Statistics and data

The state of agent tools is rebuilt every day from these probes: reachability, protocol versions, readiness, uptime, prices, access, safety, topics and growth across all three protocols. It is free to reuse under CC BY 4.0 as /stats.json and /stats/daily.csv.

Also: how many tools actually work, one page per protocol (x402, MCP, A2A), a page per topic (for example payment), monthly reports and, on every listing, how it compares with its peers. Each has a JSON twin. Search terms are counted only in aggregate (see Privacy).

Claiming a listing you operate

Almost everything here was crawled, so most listings describe someone who never asked to be indexed. If one of them is yours, you can take it over and correct it: sign in with GitHub, then publish a token we issue on the host that serves the listing — in a descriptor you already publish, in a well-known file, or as a DNS TXT record.

Nothing is required of you. Listings stay up either way and submitting one does not need an account. A verified claim gets an Owner verified badge, lets you edit the descriptive fields, and adds 3 to 5 points to the grade. Measured fields — availability, grade, latency, conformance, on-chain demand — are not editable by anyone.
